---
title: Fine-tuning datasets
---

A **fine-tuning dataset** is a set of examples, each an input paired with the exact output the model should learn to produce. It is usually stored as **JSONL**: a text file with one JSON object per line, one example per object.

An example takes one of three shapes:

- **Instruction / input / output** — three fields: the task, the material to work on (optional), and the answer. The Stanford Alpaca dataset, 52,000 examples, uses this shape.

  ```json
  {"instruction": "Classify the ticket's urgency as low, medium, or high.", "input": "Checkout fails for every customer since 9:00.", "output": "high"}
  ```

- **Chat messages** — a conversation as a list of messages, each with a `role` (`system`, `user`, or `assistant`) and its `content`. The model learns to write the `assistant` turns. This shape matches how chat models are called in production, so the fine-tuned model sees training inputs laid out like its real ones.

  ```json
  {"messages": [{"role": "user", "content": "Checkout fails for every customer since 9:00."}, {"role": "assistant", "content": "high"}]}
  ```

- **Preference pairs** — a prompt with a `chosen` and a `rejected` response, for preference tuning such as DPO (G4.3).

**Quality over quantity** — the rule that better examples help more than more examples, because the model copies what it sees, mistakes included. LIMA was fine-tuned on only 1,000 curated examples and did well; in its tests, filtering the data for quality raised answer ratings, while doubling the data from one source did not. Microsoft's guide suggests 50–100 high-quality examples for a first test, and 500 or more for a production model.

What makes an example good:

- **Correct** — the output is the answer you want in production, checked by someone who knows the task.
- **Consistent** — the same kind of input gets the same kind of output: the same labels, the same JSON keys, the same tone. Two annotators who label "urgent" differently teach the model to guess.
- **Representative** — the inputs cover what production will send, in similar proportions, including the hard and rare cases.
- **Shaped like production** — the prompt is laid out exactly as the app will send it, so the model meets familiar text after deployment.

Examples come from three places: real inputs from logs with outputs written or corrected by people, examples written from scratch by experts, and **synthetic** examples generated by a stronger model and then checked. Some examples are always held back from training, to test the result (G4.5, G2.3).
